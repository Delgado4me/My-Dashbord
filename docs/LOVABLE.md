# Lovable: перенесення та перевірки

Оновлено: 30.09.2026.

Проєкт: **My Personal Dashboard**. Ціль — продовжити наявний імпорт vanilla JS у Lovable зі збереженням зовнішнього Supabase. Додатковий фреймворк або нова база для цих змін не потрібні.

## Де працює застосунок

У Lovable головний маршрут TanStack Start відкриває `public/dashboard.html`. Сам дашборд залишається в `public/app.js`, `public/backend.js`, `public/style.css`. Markdown-читач — `public/reader.html` і `public/reader.js`.

У цьому репозиторії самостійного frontend головний HTML — `public/index.html`; для наявного імпорту Lovable ті самі зміни застосовуються до `public/dashboard.html`. Не замінюйте маршрутизатор Lovable чи `package.json` репозиторієм статичних файлів цілком. Перехід `/` → `/dashboard.html` має зберігати **і search, і hash**, інакше губиться результат Google OAuth.

## GitHub і Lovable — окремі підключення

Під час первинної перевірки `Delgado4me/My-Dashbord` був порожній; його двобічну синхронізацію з Lovable не підтверджено. За документацією, прив’язка Lovable-проєкту створює його GitHub-репозиторій; довільний уже наявний репозиторій не стає linked repo автоматично.

Перевірте **Project settings → Git → GitHub**: назву репозиторію, статус Connected, активну гілку. Працювати через GitHub із автоматичним перенесенням у Lovable можна після підтвердження саме цієї прив’язки. Копія коду в GitHub та зміни preview Lovable самі по собі не доводять наявності autosync.

## Помилка зі скриншота

Текст: `License activation limit reached`. У вихідному коді дашборда немає відповідного механізму ліцензійної активації. API Lovable під час перевірки повернув проєкт у стані `ready`, без project error; він ще не опублікований. Причину конкретного діалогу за цими даними не встановлено. Це не доведена помилка Supabase чи коду дашборда. Якщо діалог повторюється, потрібен «Get help»/підтримка Lovable з цим проєктом і часом помилки; зміна бекенду сама по собі не підтверджене виправлення.

## Що треба перевірити вручну

- Особистий вхід до **існуючого** зовнішнього Supabase.
- Прочитати лист і повернутися назад.
- Перевірити Google OAuth в окремій вкладці за дозволеною адресою.
- Перевірити список і читач Obsidian після реального commit/push.
- Екрани 360, 390 і 430 px; довгі назви, клавіатура, натискання та Android Back.

Браузерні тести з підставними даними не замінюють перевірку живих інтеграцій. Серверні налаштування та зовнішню публікацію потрібно підтверджувати окремо.

[Документація Lovable Git sync](https://docs.lovable.dev/integrations/github).

## Фактичний стан 30.09.2026

Зовнішній Supabase `kkdkqeptywizkuretujh` підключено до Lovable; проєкт ACTIVE_HEALTHY. Усі вісім таблиць дашборда мають RLS. Схему та дані не змінено.

На сервері застосовано вузьке виправлення до попереднього коду Google: `dashboard-google` v14 дозволяє точні адреси preview Lovable і старого сайту; `dashboard-google-callback` v10 повертає в Lovable. Live OPTIONS для Lovable повернув 204 з відповідним origin, сторонній origin — 403. Перевірка особистих Gmail/Calendar потребує входу користувача.

Код серверних функцій у цьому репозиторії додатково готує параметри через env. Він не тотожний вузькому live-виправленню: перед його окремим розгортанням потрібно задати параметри з `ПІДКЛЮЧЕННЯ.md`, інакше функції відмовлять у доступі.

Оновлення live-функції Obsidian не виконано: автоматична перевірка відхилила відкриття старого приватного сховища у Lovable за дозволу лише на `Delgado4me/My-Dashbord`. Для використання старого приватного джерела потрібен окремий дозвіл. Файл `notes/Початок.md` містить лише тестовий текст у дозволеному репозиторії.
